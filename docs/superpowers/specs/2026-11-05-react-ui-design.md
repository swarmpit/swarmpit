# Swarmpit React UI migration

Status: approved by the user on 2026-11-05. The user additionally requires durable instructions for future agents and explicitly authorized parallel implementation. An independent builder review found no important unanswered planning questions. Current implementation and proof are recorded in docs/UI_PARITY.md.

## Intent

Keep Swarmpit's Docker Swarm management functionality and ability to incorporate upstream changes. Replace its ClojureScript/Rum/Material UI frontend with React, TypeScript, Tailwind CSS 4, shadcn/ui, and TanStack Query. A working dashboard alone is not completion: every existing supported user flow must remain available.

Implement on a new branch based on upstream/master and push explicitly to fork if publishing is authorized; never merge the unrelated bootstrap history into upstream history or force-push either repository.
- Keep fork master as the upstream tracking branch. Maintain the custom UI on a separate react-ui branch, with ordinary feature branches as needed.
- Preserve the upstream license and attribution.

## Approaches

1. Recommended: add a separately built React frontend within the fork, calling the existing backend and preserving its data and security contracts. Keep the original frontend available during migration. This meets the requested stack while minimizing backend merge conflicts.
2. Restyle the existing Rum frontend. Rejected because it retains ClojureScript and its legacy UI dependencies rather than delivering the requested TypeScript frontend.
3. Rewrite the entire application in TypeScript. Rejected because it duplicates Docker, authorization, database, and deployment logic and makes upstream changes substantially harder to incorporate.

Only the first approach fits all stated requirements; the user approved it.

## Goals and boundaries

Preserve first-run setup, authentication, authorization, all resource operations, live updates, statistics, registry integrations, account management, existing deep links, and Docker packaging. Retain backend Clojure, request specs, CouchDB records and migrations, optional InfluxDB 1.x integration, Swarm agent, Docker mappers, and environment configuration.

Do not add a new backend service, authentication provider, database, SSR runtime, or new product features. Do not replace a working native API with duplicated business logic in React. Do not treat mock data, raw JSON forms in place of existing forms, dead controls, or legacy-page links as completed React feature parity.

## Stack and ownership

Create frontend/ as an independent Vite React TypeScript application. Use strict TypeScript. Use the Tailwind 4 Vite plugin and actual shadcn/ui components generated by its current CLI. Use TanStack Query for server state, queries, mutations, invalidation, and cancellation; use ordinary component state for transient form and UI state. Use a maintained hash router to retain existing URL semantics. Resolve the router and any editor/chart dependency against current documentation before installation; select only dependencies needed by existing features.

Registry latest versions observed on 2026-11-05: React 19.3.1, Tailwind CSS 4.3.4, shadcn CLI 4.23.0, TypeScript 7.0.2, TanStack React Query 5.106.1, Vite 8.3.6. Recheck stable releases and Node engine compatibility at implementation time. Use Tailwind major 4 as explicitly requested even if a new major becomes available. Commit a lockfile when committing implementation is authorized. shadcn distributes source components: its CLI version does not mean every component is an independent package at that version.

Suggested structure: frontend/src/app for providers, layout and routing; frontend/src/components/ui for generated shadcn components; frontend/src/lib for the HTTP client and formatting; frontend/src/features/<domain> for typed contracts, queries, components, and pages. Add helpers only where behavior is shared. Do not introduce a generic resource framework that obscures domain forms or permissions.

## Backend contracts verified in code

The source of truth is executable code, not statements in upstream CLAUDE.md. That document contains stale descriptions of token formatting and version paths.

- POST /login accepts Authorization: Basic <base64 credentials>. Its token response already contains the Bearer prefix, produced by token/generate-jwt. Store and send the returned authorization value unchanged; do not add a second prefix or strip the existing one.
- Keep the existing localStorage token key for session compatibility. Handle unavailable or malformed stored values. Read /api/me for current user data; backend authorization remains authoritative. Never use client-decoded claims as authorization.
- POST /logout revokes the login token. Call it, then clear credentials, all user-specific query data, active streams and timers. Expose backend failures without leaving privileged cached views visible. Separate API tokens from login tokens.
- GET /version is public and supplies initialization/version/configuration information. It is not /api/version. First-run setup uses POST /initialize; preserve backend username/password validation and the already-initialized refusal.
- Password and API token management use /password and /api-token. Preserve generate, replace and revoke semantics and one-time sensitive-value presentation.
- Backend rules distinguish admin, user, viewer and registry ownership/public access. Node mutations and user administration require admin privileges. Match controls to capabilities, preserve forbidden/error pages, and let the backend reject unauthorized requests. Pin/unpin is allowed to authenticated users under current rules.
- HTTP success can be 200, 201 or 202 with an empty body. The client must not unconditionally parse JSON. Preserve useful backend errors and X-Backend-Server distinctions: a 401 from the Swarmpit session boundary is different from invalid credentials returned by a registry operation.
- Native fetch with AbortSignal is sufficient for HTTP. Encode path segments and query values, send JSON bodies explicitly, and make Accept application/json explicit. Do not change POST mutations into PATCH or PUT without an existing backend route.

## Live updates

Retain the backend SSE protocol. Obtain a fresh short-lived token from GET /slt using the login authorization header. Connect EventSource to /events with slt and subscription query parameters. The subscription is a base64-encoded EDN route map with keyword handler and params, not JSON. Preserve the legacy handler names and exact parameter shapes expected by event rules. The encoder only needs the known route-map shape; encode strings safely rather than interpolating resource names into EDN.

Short-lived tokens are consumed by the backend on connection. On reconnect, close the previous EventSource and obtain a new token rather than blindly reusing its URL. Keep at most one active subscription for the mounted route, cancel in-flight token requests when navigation occurs, and clear retries on route change/logout. Resume with fresh HTTP data as appropriate after a disconnect so the view does not remain stale.

Incoming data contains domain snapshots rather than generic invalidation messages. Map these snapshots into the appropriate query keys; invalidate related data only where needed. Dashboard includes personalized pins, services, nodes, and optional timeseries. Task detail subscriptions use serviceName; service detail accepts name or ID; stack detail uses name. Keep existing nullable statistics behavior when InfluxDB is absent or unavailable. Preserve the service log retrieval path and agent/native fallback implemented by the backend.

## UI direction (implementation defaults proposed)

Use a compact operations console: persistent responsive sidebar, clear page titles and primary actions, searchable resource tables, detail tabs, status badges with text, readable logs and compose editing. Use neutral shadcn styling with a restrained accent, light/dark themes following system preference with an explicit stored toggle. Preserve the Swarmpit identity and instance name. This visual direction is a proposal; no reference design was provided.

Use semantic tables, labels, accessible dialogs, focus management and keyboard navigation. Status must not depend solely on color. Forms must preserve upstream distinctions, defaults and validation. Preserve unsaved edits while background queries refresh; refetching must not reset dirty fields. Revalidate payloads using the existing backend; display field and backend errors. Show a focused confirmation for destructive actions and wait for the mutation result before claiming success. Never retry destructive mutations automatically.

## Build, deployment and rollback

Keep legacy ClojureScript source and its default packaging initially. Serve the built React app separately during migration, with same-origin backend requests. Development Vite proxy must include /api, /login, /logout, /version, /initialize, /password, /api-token, /slt and /events, with streaming behavior preserved.

For a reviewable side-by-side deployment, bundle Vite output under resources/public/react/ with base /react/ and use hash routes there. The default legacy / entry remains available until parity gates pass. Native classpath static-resource serving should own React files; confirm GET /react/index.html and assets work before adding backend routing. Avoid changing authentication or API routes just to serve assets. Test the actual index template behavior rather than replacing it blindly: handler/index-page appends legacy css/main.css and js/main.js.

Add a separate production build path for the custom UI using the current Java/Leiningen build and a Node asset-build stage, without requiring Node in the final runtime. Once parity is verified, select React for the custom image's default entry using a narrowly scoped template/entry integration. Keep an explicit legacy image/build or entry rollback available. Preserve existing volumes, service definitions, database configuration and Docker API negotiation. No database migration should be needed for this UI change.

## Upstream updates

Maintain true fork history. Merge upstream/master into react-ui through a reviewable update branch. Preserve local frontend files; resolve template/build integration conflicts explicitly. Review diffs to routes.cljc, routes_spec.cljc, token/authentication/authorization, handlers, version metadata and event rules against the React contracts and feature checklist.

Implement a scheduled and manually triggered GitHub Actions workflow that opens an upstream-update pull request when changes exist. Do not automatically merge or deploy upstream changes. Use repository-scoped credentials with minimal permissions, a fixed update branch with concurrency protection, and skip gracefully when there is no diff. Merge conflicts must be surfaced for manual resolution instead of discarding either side. The workflow's PR must run the same backend/frontend and packaging checks; use an event/token strategy that actually triggers these checks rather than assuming PRs created with GITHUB_TOKEN trigger normal pull_request workflows. Keep the original master build workflow behavior isolated from the custom image build; do not publish under the upstream project's Docker Hub namespace.

This means receiving and reviewing updates automatically, not promising zero-maintenance UI compatibility. New upstream screens/actions require React ports. Backend/security changes must be tested before deployment.

## Implementation sequence

1. Start a branch from the recorded upstream baseline without destroying the existing workspace bootstrap branch/assets. Inventory routes and actions and turn the parity table into a tracked implementation checklist.
2. Build the frontend toolchain, generated shadcn primitives, shell, theme, routing, typed fetch, authentication/setup, capability checks and SSE lifecycle. Prove login and a real backend-backed resource list.
3. Port read views and live updates for all resource domains, dashboard, logs and charts.
4. Port every mutation and complete domain form, including service wizard/configuration, stack history/lifecycle and provider-specific registries. Verify round trips and permission behavior.
5. Add production asset packaging, the custom-image entry and legacy rollback. Add update PR automation and CI tied to actual repository branches.
6. Complete parity acceptance checks against a disposable Docker Swarm and package the deployable result. Do not declare completion if production Docker integration has not been verified.

## Verification and completion criteria

- Frontend typecheck, production build and focused tests of authorization-value handling, 401/403 classification, empty-body responses, safe SSE subscription encoding and reconnect cleanup.
- Meaningful tests for mutation payloads and invalidation, dirty form preservation, first-run/session/logout flows, role-restricted actions, and the most complex service/stack forms.
- Existing lein check and unit suite for backend/integration edits. Run integration tests using the project's documented disposable Docker setup where available.
- End-to-end operations on a disposable Swarm: create/edit/redeploy/rollback/stop/delete service, deploy/edit/deactivate/reactivate/delete stack, node management, network/volume/secret/config operations, registry image selection, user/admin/viewer permissions, dashboard pins, logs, live updates and optional metrics absence. Never use a production Swarm for destructive verification.
- Build the production image and verify its real entry, assets, API calls and SSE. Verify the legacy rollback path and preserve existing data on switching images.
- Exercise the upstream workflow's no-change, update and conflict cases, and confirm update PR checks actually run. Preserve a clean no-op update when already current.
- If Docker, registry credentials or CI credentials are unavailable, report the exact unverified flows. A passing static frontend build alone does not establish feature parity.
